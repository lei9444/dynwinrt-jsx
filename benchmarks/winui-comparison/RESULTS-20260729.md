# WinUI comparison benchmark — 2026-07-29

This document records the first formal comparison between:

- direct imperative C# WinUI;
- dynwinrt-jsx fine-grained Signals;
- Microsoft.UI.Reactor's optimized reconciler path.

It documents the workload, execution protocol, metric semantics, result
interpretation, and the scenarios that are still missing. The raw run is stored
locally under:

```text
benchmarks/winui-comparison/results/formal-20260729/
```

The results directory is intentionally ignored by Git because it contains
per-process logs and machine-specific output. This document preserves the
baseline summary in source control.

## Implementations

| Variant | Implementation |
|---|---|
| `Direct` | `microsoft-ui-reactor/tests/stress_perf/StressPerf.Direct` |
| `DynWinRTJsx` | `benchmarks/winui-comparison/dynwinrt-jsx` |
| `Reactor` | `microsoft-ui-reactor/tests/stress_perf/StressPerf.ReactorOptimized` |

The direct and Reactor variants are the existing Microsoft.UI.Reactor
StressPerf applications. The dynwinrt-jsx variant ports the same StockGrid
workload.

## Workload

Every implementation creates:

- a 70 x 70 Grid;
- 4,900 native WinUI `TextBlock` controls;
- 64 x 18 pixel cells;
- font size 8;
- text plus foreground-color updates;
- one attempted update every 33 ms;
- deterministic stock-price mutation.

The workload uses the same `System.Random(42)` sequence. The JavaScript
implementation contains a compatible seeded .NET Random algorithm and verifies
its first values against .NET:

```text
Next(4900) = 3273
NextDouble() = 0.14090729837348093
Next(4900) = 615
NextDouble() = 0.5227642760252413
```

The mutation count is:

```text
max(1, floor(4900 * percent / 100))
```

Therefore the `0%` scenario still mutates one randomly selected cell per tick.
Duplicate indices within one tick remain possible in every implementation.

### Direct WinUI

The Direct variant keeps references to every native TextBlock. Each timer tick
mutates the data source and assigns `Text` and `Foreground` directly on changed
controls.

### dynwinrt-jsx

The formal baseline used the original split binding mode. Each cell owns:

- one text Signal;
- one foreground Signal;
- property effects that assign the corresponding native TextBlock properties.

Changed cells are updated in one `batch()`:

```ts
batch(() => {
  for (const change of changes) {
    cells[change.index].text.value = formatCell(change.item)
    cells[change.index].foreground.value =
      change.item.isUp ? greenBrush : redBrush
  }
})
```

The component function does not rerender. Signal effects directly patch the
real native controls.

The benchmark application also supports an experimental grouped mode in which
one cell Signal and one property effect assign both `Text` and `Foreground`.
That mode was added after the formal baseline and is reported separately below.

### Microsoft.UI.Reactor

The ReactorOptimized variant creates a new data snapshot, renders an element
tree, memoizes unchanged cells by index, reconciles the tree, and patches real
WinUI controls.

## Execution protocol

The formal command was:

```powershell
.\benchmarks\winui-comparison\run-comparison.ps1 `
  -ReactorRoot ..\microsoft-ui-reactor `
  -DotnetPath C:\Users\leilzh\.dotnet10latest\dotnet.exe `
  -Percents 0,50,100 `
  -Duration 10 `
  -Warmup 2 `
  -Reps 12 `
  -SkipBuild `
  -OutDir .\benchmarks\winui-comparison\results\formal-20260729
```

For each mutation percentage:

```text
14 rounds * 3 processes
= 2 warmup rounds + 12 measured rounds
```

The execution order rotates by round:

```text
Direct -> DynWinRTJsx -> Reactor
Reactor -> Direct -> DynWinRTJsx
DynWinRTJsx -> Reactor -> Direct
```

This reduces fixed ordering bias from thermal state, CPU frequency, background
activity, and machine drift.

The run used:

- Release builds;
- x64 processes;
- Node.js 24.18.0;
- .NET SDK 10.0.302;
- Windows 10.0.26100;
- AMD EPYC 7763;
- High Performance power plan;
- 2 discarded warmups;
- 12 measured repetitions.

The terminal was not elevated, so ETW Present tracing was not collected.

## Metrics

### Completed updates per second

Each implementation increments `TotalRenders` after one update has completed
according to that framework:

| Variant | Completion point |
|---|---|
| Direct | Changed native properties were assigned |
| dynwinrt-jsx | The Signal batch flushed its property effects |
| Reactor | Reactor reported reconcile completion |

The headline value is normalized using the requested ten-second measurement
window:

```text
completed updates / 10 seconds
```

This is a framework throughput proxy. It is not actual displayed FPS.

### Synchronous update/commit latency

| Variant | Included work |
|---|---|
| Direct | data mutation and direct native property assignment |
| dynwinrt-jsx | data mutation, Signal writes, scheduling, effects and native property assignment |
| Reactor | update dispatch plus tree build, reconcile/diff, patch and effects |

These values do not include all deferred WinUI layout, text shaping, render
thread, compositor, or DWM work. They describe framework-side synchronous
callback cost, not pixel latency.

### Memory and CPU

The runner samples the process externally every 100 ms:

- peak `WorkingSet64`;
- total process CPU time;
- process-to-window-ready time.

External Working Set is used because C# managed allocation and V8 heap are not
equivalent. Runtime-specific allocations remain available in raw results but
must not be directly compared byte-for-byte.

### Statistics

The summary reports the median of 12 measured runs for each absolute metric.

Relative comparisons pair each variant with Direct from the same round:

```text
deltaPercent = (variant - direct) / direct * 100
```

The paired delta table reports:

```text
mean +/- 1.96 * sampleStandardDeviation / sqrt(12)
```

If the 95% interval does not include zero, the direction was stable in this
run. This interval is not a substitute for cross-machine replication.

## Interpretation

### What the run shows

- Direct WinUI has the lowest framework callback latency, startup time, memory,
  and total CPU cost.
- dynwinrt-jsx avoids full component rerenders and has low single-cell Signal
  cost, but 4,900 native wrappers plus 9,800 cell Signals/effects have a large
  startup and memory cost.
- At 50% mutation, dynwinrt-jsx and Reactor have similar synchronous callback
  cost, while dynwinrt-jsx completes more update passes.
- At 100% mutation, dynwinrt-jsx callback cost is higher than Reactor's,
  suggesting COM property writes and thousands of Signal/effect notifications
  dominate when nearly the whole tree changes.
- Node/V8, the Worker, generated binding module loading, projected wrappers and
  reactive graph explain much of dynwinrt-jsx's fixed startup/RSS overhead.

### What the run does not prove

It does not prove that dynwinrt-jsx displays more frames or looks smoother.
`CompositionTarget.Rendering` is not an authoritative FPS metric because it can
fire when no new image is presented.

The final visual comparison requires an elevated run with:

```powershell
-IncludeEtw
```

That records per-process `DxgKrnl::Present` events, Present/s, p50/p95 frame
intervals, and global VSync.

CPU time currently covers startup, measurement, and shutdown. A future
measurement handshake should capture CPU only during the steady-state window.

### Startup-stage instrumentation

StockGrid runs now preserve framework-specific startup profiles in `raw.jsonl`.
dynwinrt-jsx reports component/VNode build, native mount, activation, Loaded,
and first-frame milestones. ReactorOptimized reports its built-in
`OnRenderComplete` tree-build, reconcile, and effects timings plus first frame.

A one-repetition parser smoke with the normal dynwinrt projection produced:

| Variant | First frame | Tree build | Reconcile/native mount |
|---|---:|---:|---:|
| dynwinrt-jsx | 5,338.5 ms | component/VNode bucket available in raw data | 3,810.0 ms native mount |
| ReactorOptimized | 1,665.1 ms | 54.2 ms | 491.2 ms reconcile |

This smoke validates instrumentation boundaries only. It is not a replacement
for the warmup/repetition protocol or ETW Present tracing, and the two
frameworks' internal buckets are not semantically identical.

## Post-baseline optimization experiments

These experiments use the same StockGrid workload but are not part of the
12-repetition formal tables above. They are directional engineering evidence,
not publication-quality framework comparisons.

### Grouping related native property writes

`adapter.oneWay(setter)` allows one observer to assign multiple related native
properties. Changing each cell from two Signals/effects to one grouped
Signal/effect produced:

| Mutation | Average callback | p95 callback | V8 heap |
|---:|---:|---:|---:|
| 50% | about 58.0 -> 48.0 ms | about 75.3 -> 57.4 ms | lower, but GC-sensitive |
| 100% | about 114.1 -> 86.9 ms | improved | about 141 -> 75 MB |

This is the strongest optimization measured so far. Dense cells should group
properties that always change together instead of creating one observer per
native property.

### Reducing Inspector detail

Disabling detailed node and subscription tracking reduced a representative V8
heap result from about 105.7 MB to 93.7 MB and slightly improved startup/update
time. External RSS did not improve consistently, so reduced Inspector detail
remains an explicit production profile rather than a claimed process-memory
fix.

### Lazily allocating Scope containers

`ScopeImpl` previously allocated six containers for every scope, including
empty child, context, mount, observer, cleanup, and subscribed-dependency
collections. These containers are now created on first use and removed again
when empty.

A focused A/B used grouped cells, full Inspector detail, 5-second runs, and
three repetitions at each mutation level. The eager control used the same
source tree with only the Scope-container change removed.

| Mutation | Metric | Eager | Lazy | Change |
|---:|---|---:|---:|---:|
| 50% | V8 heap | 125.99 MB | 119.91 MB | -4.8% |
| 50% | Average callback | 49.95 ms | 49.68 ms | -0.5% |
| 50% | External peak RSS | 672.69 MB | 675.79 MB | +0.5% |
| 100% | V8 heap | 92.89 MB | 85.55 MB | -7.9% |
| 100% | Average callback | 92.36 ms | 94.04 ms | +1.8% |
| 100% | External peak RSS | 702.60 MB | 709.71 MB | +1.0% |

The V8 heap reduction was consistent enough to retain. Callback latency,
p95 latency, startup, and external RSS did not show a stable improvement, so
this change is classified only as a JavaScript-heap optimization.

### Lazily allocating Signal dependency collections

Every Signal also previously allocated both an observer Set and a listener Set
at construction. Most application state Signals have no direct
`.subscribe()` listeners, and some Signals are not observed until a branch
mounts.

An isolated Node `--expose-gc` allocation test loaded the package before the
memory baseline, forced GC, retained all created Signals, forced GC again, and
repeated each case three times:

| Case | Count | Eager bytes/Signal | Lazy bytes/Signal | Saving |
|---|---:|---:|---:|---:|
| No observer or listener | 500,000 | 384.0 B | 80.0 B | 304.0 B / 79.2% |
| One effect observer, no listener | 200,000 | 856.3 B | 704.3 B | 152.0 B / 17.8% |

The observed case matches grouped StockGrid cells: their observer Set is
required, while the empty listener Set is not. End-of-run StockGrid heap
samples remained sensitive to V8 GC timing, so this isolated allocation result
is the evidence for retaining the change; no additional callback-latency or
external-RSS claim is made.

The publish path now also skips collection snapshots when no observer/listener
collection exists and directly traverses observers while notification delivery
is deferred. Five isolated repetitions of 10 million unobserved Signal writes
had these medians:

| Publish implementation | Median total | Median per write |
|---|---:|---:|
| Eager empty-collection snapshots | 296.35 ms | 29.6 ns |
| Lazy no-collection path | 85.19 ms | 8.5 ns |

For 10,000 observed Signals updated 50 times in batches, the median remained
effectively unchanged at about 17.4 microseconds per publish because scheduling
and running the native-property-style effects dominate. The fast path is
therefore useful for unobserved/transient state, but is not presented as a
StockGrid callback improvement.

### Deferred dynwinrt projection fast paths

A local dynwinrt runtime/codegen prototype tested:

- cached default activation factories and lazy `ActivateInstance` handles;
- typed property-setter calls that avoid per-call method/value wrappers;
- typed one- and two-argument `void` method calls.

Short same-machine runs showed substantial potential for the factory/property
setter portion:

| Metric | Existing projection | Prototype |
|---|---:|---:|
| Blank first frame | about 720 ms | about 529 ms |
| 4,900-control window ready | about 5,354 ms | about 2,451 ms |
| 50% average callback | about 57.8 ms | about 37.4 ms |
| 100% average callback | about 102.8 ms | about 61.8 ms |

The general `void` method extension added only about another 6% mount
improvement and required special exclusions such as scheduled
`Application.Start`. Later cast-combination and direct struct-packing
experiments provided only small or negative results.

All dynwinrt performance changes were removed after the experiment. The
optimization remains a future direction, but it must be redesigned with:

- runtime/codegen capability or version gating;
- differential old/new generated-binding behavior tests;
- primitive-width, null, object-interface, struct, error, async, and special
  method coverage;
- full Dashboard/Gallery native lifecycle and UI Automation validation.

The current benchmark and generated bindings use the normal released dynwinrt
projection path.

### JSX architecture validation matrix

The architecture-level claims were rechecked with the normal dynwinrt
projection and interleaved local runs:

| Optimization | Evidence | Result |
|---|---|---|
| Group related property observers | StockGrid split vs grouped, three runs per mutation level | 50% average callback 65.4 -> 50.2 ms (-23%); 100% 123.2 -> 90.4 ms (-27%) |
| Lazy Scope/Signal collections | Isolated retained-allocation test with forced GC | Empty scope 992 -> 136 B; unobserved Signal 384 -> 80 B; one-effect Signal 856 -> 704 B |
| Production Inspector profile | Four interleaved full/minimal StockGrid runs | V8 heap 56.4 -> 49.4 MB (-12%); first frame improved about 58 ms / 1.2%; external RSS unchanged |
| Native ItemsRepeater virtualization | 100/1,000/5,000 item scroll runs | 1,000 and 5,000 items retained about 314 and 303 active native nodes respectively; active tree did not grow with item count |
| Gallery page-module laziness | WinAppSDK/STA module-load probe | Full `app.js`: about 2,037 ms, 183 Gallery + 480 binding modules. Home-only module: about 1,612 ms, 5 Gallery + 465 binding modules |

Gallery route pages now use the public `createLazyComponent()` synchronous
loader. Cold `app.js` loading
changed from about 2,037 ms / 183 Gallery modules / 480 binding modules to
about 1,713 ms / 31 Gallery modules / 466 binding modules. Router UI Automation
also passed repeated lazy Binding/Templates navigation.

Scoped last-value coalescers and composition-frame scheduling now support
PointerMoved-style event delivery. ScrollViewer controllers expose immediate,
frame, and native sampling. In an isolated 100,000-event Signal workload,
immediate delivery took a 46.45 ms median and ran the effect 100,001 times;
coalesced delivery took 1.85 ms and ran it twice.

Initial empty-collection `replaceAll` batching was implemented and tested, but
did not improve StockGrid native mount (3,456.5 ms control versus 3,465 ms
batch). It was removed rather than retaining an unproven path.

## Is StockGrid the only benchmark?

StockGrid is currently the only implemented cross-framework scenario. It is a
macro benchmark for a fixed, fully realized property-update tree. It does not
exercise every framework design trade-off.

Startup, KeyedList, VirtualList, and the comparable ControlModel micro subset
now have cross-framework runners and one-repetition smoke comparisons. They
are not included in the formal StockGrid tables above until baseline-quality
warmup/repetition runs are captured.

The comparison suite should grow in this order:

| Priority | Scenario | Main path measured |
|---:|---|---|
| 1 | Startup: empty window and 4,900-cell window | module load, projection creation, first activation/present |
| 2 | Keyed list reorder/insert/remove | keyed identity, LIS/diff, native movement |
| 3 | Mount/unmount branch replacement | scope creation/disposal, subscriptions, native lifetime |
| 4 | Virtualized scrolling list | realization, recycling, JS/C# callback pressure |
| 5 | High-frequency PointerMoved | event crossing, frame coalescing, dropped/intermediate values |
| 6 | ScrollViewer state synchronization | immediate vs frame-coalesced sampling |
| 7 | Long-lived 30-minute heap stability | wrapper retention, GC pressure, cleanup failures |
| 8 | Controlled TextBox/selection | native echo suppression and accepted/rejected updates |
| 9 | Theme/resource refresh | resource lookup and subtree property refresh |

Reactor already contains Direct/Reactor keyed-list, virtualization, Flex and
DataGrid stress applications. The dynwinrt-jsx suite can port the scenarios
that map to existing framework capabilities and use the same runner protocol.

### Control-model micro-suite

`PerfBench.ControlModel` removes most WinUI rendering noise and measures
nanoseconds/op plus managed bytes/op.

| Bench | Reactor scenario | Closest dynwinrt-jsx scenario |
|---|---|---|
| M1 | Mount one leaf, no callback | Mount one native TextBlock |
| M2 | Mount leaf with one callback | Mount ToggleSwitch with one event |
| M3 | Mount leaf with three callbacks | Mount Button with three subscriptions |
| M4 | Cold dispatch across element types | Cold native-constructor/adapter lookup |
| M5 | Warm dispatch | Warm native factory lookup |
| M6 | External registered type | Custom `native()` adapter |
| M7 | Update 1,000-element tree with no changes | Signal no-op writes / unchanged property path |
| M8 | One leaf changed | One Signal-to-native property update |
| M9 | Every property changed | Full Signal/native property sweep |
| M10 | Event-handler state allocation | Event subscription allocation |
| M11 | Modifier/event-state frequency | Property adapter and subscription churn |
| M12 | Pool rent hot path | Native virtualization recycle path, not ordinary JSX |
| M13 | Setter suppression scope | Controlled-property echo suppression |
| M14 | Deep DSL rebuild cascade | Not equivalent: JSX components do not rerender as a tree |

M1–M3, M7–M10 and M13 can be ported with meaningful semantic equivalence.
M4–M6 are framework dispatch internals and should be labelled separately.
M12 measures Reactor pooling; the comparable JSX path is ItemsRepeater
recycling rather than ordinary component mount. M14 intentionally measures
Reactor's virtual-tree DSL rebuild and has no direct Signal equivalent.

### Startup suite

Reactor includes:

- `BlankWinUI3`
- `BlankReactor`
- `BlankReactorMsix`
- `BlankRNW`

The suite records startup milestones such as process start, first component
render, Window loaded/activated and first present. A dynwinrt-jsx startup leg
should additionally split:

- Node/V8 startup;
- Windows App SDK bootstrap;
- Worker creation;
- generated-binding module load;
- `Application.startScheduled()`;
- first native tree mount;
- Window activation;
- first ETW Present.

### Command benchmark

`tests/cmd_perf` compares:

- Reactor commanding;
- XAML command objects;
- WPF commands.

It is relevant after dynwinrt-jsx has a first-class command model. Until then,
measuring raw Button callbacks against Reactor command records would compare
different feature sets.

### Recommended implementation order

The next comparable additions should be:

1. blank and loaded startup;
2. keyed-list structural churn;
3. native and framework virtualized lists;
4. M1–M3 mount/event subscription;
5. M7–M9 no-op/one-change/all-change update micros;
6. M10/M13 event allocation and controlled echo suppression;
7. 30-minute memory/cleanup stability;
8. high-frequency pointer and scroll coalescing.

Flex, DataGrid, command, off-thread and time-slice comparisons should wait
until dynwinrt-jsx exposes equivalent behavior.

## Publication requirements

Before citing results externally:

1. Run in an elevated terminal with ETW enabled.
2. Lock display refresh to a fixed value and disable Dynamic Refresh Rate.
3. Keep the benchmark window foreground and unoccluded.
4. Repeat on at least one physical x64 and one physical ARM64 machine.
5. Separate engine/runtime fixed memory from per-control memory using an empty
   window baseline.
6. Capture CPU and allocations only inside the measured steady-state window.
7. Publish raw JSONL, environment metadata, commit SHAs, and confidence
   intervals with the summary.
